## Executive Summary

**Главный вывод:** страница смешивает два разных уровня — **контур (среда)** и **компанию (tenant)** — в одной визуальной форме. Это создаёт путаницу уже сейчас и **не масштабируется** при росте числа клиентов.

**Рекомендуемая модель:** **гибрид A+** — объект страницы = **релизный контур платформы (среды)**, а для `CLIENT` — отдельный **флот компаний** (не третья «равная» карточка рядом с DEV и Template).

**Вердикт:** страница **нужна** (не вариант В), но концепция отображения требует пересборки.

## Задача 1. Продуктовая сущность

### Что показывает страница сейчас (по факту)

| Уровень | Что в UI | Что в данных |
|---------|----------|--------------|
| Карточка 1 | Среда **DEV** + компания «Разработка» | `tenant_id=1`, `environment_key=DEV` |
| Карточка 2 | Среда **Template** + компания «Эталон» | `tenant_id=2`, `environment_key=TEMPLATE` |
| Карточка 3 | Среда **Client** + компания «Розетка» | `tenant_id=21`, `environment_key=CLIENT` |
| История | Среда + компания + версия | `platform_version_history` per `tenant_id` |

**Факт:** UI одновременно называет и **среду**, и **компанию** на одном уровне иерархии. В БД источник истины — **запись per portal** (`platform_environment_versions.tenant_id` unique), с денормализованным `environment_key`.

### Что должна показывать (архитектура релизов)

По `CODE_RELEASE_FOUNDATION_MVP.md` и Phase 1:

```text
Релизный контур: DEV → Release → Template → Release → Client(s)
```

Страница должна отвечать:

1. **На каком этапе контура** сейчас стоит платформа (DEV / Template / Client).
2. **Какая версия** активна на каждом этапе.
3. **Для Client** — какие компании получили эту версию (флот, не одна карточка).

### Объект управления

| Уровень | Объект | Когда |
|---------|--------|-------|
| **Pipeline** | **Среда** (`dev`, `template`) | Build, promote, эталон |
| **Rollout** | **Компания** (`target_tenant_id`) | Доставка в Client |
| **Аудит** | **Deployment** (будущий `CodeDeployment`) | Запись apply/rollback |

**Ответ:** объект управления **не один**.  
- Для DEV и Template — **среда** (singleton slot).  
- Для Client — **компания** (множество tenant), внутри среды `CLIENT`.

Текущая страница ошибочно представляет Розетку как третий «контур», равный DEV и Template.

## Задача 2. Масштабируемость

### Сейчас (3 tenant)

```text
DEV      → 1 portal  → 1 карточка  ✓
Template → 1 portal  → 1 карточка  ✓
Client   → 1 portal  → 1 карточка  ✓ (случайно работает)
```

### Через год (N клиентов)

```text
DEV      → 1
Template → 1
Client   → Розетка, СДС, Газпром, РЖД, Лукойл, Росатом, …
```

| Модель | Масштабируемость |
|--------|------------------|
| 3 равные карточки (текущая) | **Ломается** — 10+ карточек «Client» или потеря отдельных компаний |
| Карточки только сред | **Частично** — не видно, у кого из клиентов какая версия |
| 2 карточки сред + таблица клиентов | **Да** — фиксированный pipeline + растущий флот |

**Ответ:** текущая модель **не сохранит смысл** при десятках клиентов. Нужно разделение: **фиксированные слоты DEV/Template** + **динамический список Client deployments**.

## Задача 3. Связь с релизным контуром

```text
DEV → Release → Template → Release → Client
```

| Шаг | Уровень установки версии | Технический target |
|-----|--------------------------|------------------|
| DEV | **Среда** | `environment_key=dev`, portal id=1 |
| Template | **Среда** | `environment_key=template`, portal id=2 |
| Client | **Компания** (внутри среды CLIENT) | `environment_key=client` + `target_tenant_id` |

**Ответ:** установка версии происходит **на уровне среды** для DEV/Template и **на уровне компании** для Client rollout. Это не противоречие — это **два уровня одной модели**.

Phase 1 registry (`platform_environment_versions`) сейчас хранит всё как `tenant_id` — технически верно для MVP, но UI не должен рисовать все tenant как «среды».

## Задача 4. Совместимость с будущими сущностями

| Сущность | С чем связывается версия | Связь со страницей «Версии» |
|----------|--------------------------|------------------------------|
| **Build Registry** | `CodeBuild` при сборке из git; head привязан к **DEV** | Показать «версия DEV-сборки» на карточке DEV |
| **Release Package** | Immutable artifact; **не привязан** к одной компании | Отображается как версия на этапах контура |
| **Deployment Registry** | `CodeDeployment`: `environment_key` + `target_tenant_id` (для client) | История страницы = read-model deployments |
| **Rollback Registry** | `CodeDeploymentRollback` → конкретный **deployment** (часто per client) | Блок истории / статусы rollback |

**Вывод:** будущая модель **подтверждает гибрид** — не чистый вариант А и не чистый Б.

## Задача 6. Рекомендованная модель

### Вариант А — страница показывает среды

| | |
|--|--|
| **Плюсы** | Соответствует pipeline DEV→Template→Client; фиксированная структура; понятно владельцу продукта |
| **Минусы** | Не показывает детально каждого клиента |
| **Риски** | Без подраздела Client флот «потеряется» |
| **Масштабируемость** | Высокая для DEV/Template; для Client нужен доп. блок |

### Вариант Б — страница показывает компании

| | |
|--|--|
| **Плюсы** | Прямой ответ «у Розетки 1.0.0» |
| **Минусы** | Дублирует «Компании»; DEV/Template выглядят как «ещё компании» |
| **Риски** | Контур релиза не виден; при 50 клиентах — копия Companies |
| **Масштабируемость** | **Низкая** |

### Вариант В — страница не нужна

| | |
|--|--|
| **Плюсы** | Меньше дублирования |
| **Минусы** | Нет места для истории, pipeline, deployment audit |
| **Риски** | Потеря фундамента Code Release |
| **Масштабируемость** | n/a |

### Итоговая рекомендация: **A+ (гибрид)**

```text
Верх страницы «Версии»:
  • 2 карточки контуров: DEV, Template (объект = среда)
  • Без акцента на названии компании (или мелкий подзаголовок «портал: …»)

Блок Client:
  • Заголовок «Клиентские поставки»
  • Таблица компаний: компания | версия | дата | статус | отставание
  • Масштабируется на N клиентов

Низ страницы:
  • История версий / deployments (журнал)
```

**Не рекомендуется:** три равные карточки DEV / Template / Розетка.

## Что увидит владелец продукта

**Что сейчас концептуально неправильно**

Страница называет «Розетку» так же, как «DEV» и «Эталон» — будто это три одинаковых «среды». На самом деле Розетка — **клиентская компания**, а DEV и Эталон — **этапы выпуска платформы**.

**Почему это путает**

Когда появятся СДС, Газпром и другие клиенты, непонятно: добавлять ли им отдельные «карточки сред» или смотреть в «Компании». Два экрана показывают версию, но по разной логике.

**Как должна выглядеть страница через год**

Сверху — **два фиксированных блока**: «Что сейчас в разработке (DEV)» и «Что в эталоне (Template)».  
Ниже — **список клиентов**: у кого какая версия установлена, кто отстаёт, когда обновляли.  
Внизу — **история**, кто и когда менял версии.

Так виден **путь релиза**, а не просто три названия.
