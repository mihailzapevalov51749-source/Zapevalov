## 1. Назначение документа

Документ фиксирует **состав, назначение и границы модулей** платформы ЯсноПро — категории «Модули» из [Архитектурной классификации](./YASNOPRO_ARCHITECTURE_CLASSIFICATION.md).

Документ нужен, чтобы:

- иметь единый источник истины для реестра «Модули платформы» в DEV Studio;
- отделить **модули платформы** от [ядра](./YASNOPRO_CORE_ARCHITECTURE.md), [служб](./YASNOPRO_PLATFORM_SERVICES.md), runtime и UI-компонентов;
- **строго разделить** модули платформы и **решения, собранные на платформе**;
- классифицировать новые возможности по [Методике классификации](./YASNOPRO_ARCHITECTURE_CLASSIFICATION_METHODOLOGY.md);
- формировать Release Scope и каталог решений для партнёров и клиентов.

Документ основан на аудите **WI-ARCH-MODULES-001**, нормализации реестра **WI-ARCH-REG-MOD-002** и синхронизации **WI-ARCH-DOC-003**.  
Состав модулей v1.2 — **6 элементов** (см. раздел 4).  
Техническая реализация, API, код и таблицы БД **не входят** в scope документа.

## 2. Что такое модуль платформы

**Модуль платформы** — это самостоятельная **пользовательская возможность** платформы, которая предоставляет **бизнес-ценность** конечному пользователю и использует ядро и службы платформы.

Модуль **не является**:

- **ядром** — базовым механизмом конструктора;
- **службой** — инфраструктурным сервисом для других подсистем;
- **runtime** — средой DEV / TEMPLATE / CLIENT;
- **компонентом** — переиспользуемым UI-виджетом.

### Модуль платформы vs решение на платформе

| | **Модуль платформы** | **Решение на платформе** |
|---|---------------------|--------------------------|
| **Что это** | Возможность **самой платформы** | Прикладная система **для отрасли/функции** |
| **Примеры** | Чат, Календарь, Документы, ЯСИИ | CRM, Service Desk, HRM, Закупки |
| **Как появляется** | Поставляется платформой, включается в tenant | Собирается из объектов, полей, процессов, отображений |
| **Кто создаёт** | Команда платформы | Аналитик, интегратор, клиент в Studio |

**Модуль платформы** — пользователь видит продукт платформы («открой чат», «открой календарь»).  
**Решение на платформе** — пользователь видит предметную область («CRM», «управление проектами»), собранную конструктором.

### Место модулей в архитектуре

```text
Ядро          — как устроена компания как система
  ↓
Службы        — как платформа технически обеспечивает работу
  ↓
Модули        — какие пользовательские возможности получает компания
  ↓
Пользователь  — сотрудник, руководитель, администратор
```

Runtime (DEV / TEMPLATE / CLIENT) **размещает** ядро, службы и модули, но не является модулем.

## 3. Критерии включения в модули

Элемент включается в модули v1.0, если выполняются **все** условия:

1. **Пользователь видит функциональность напрямую** — отдельный продуктовый контур или явная user-facing capability.
2. **Пользователь получает бизнес-ценность** — можно объяснить ценность без знания архитектуры.
3. **Модуль можно отключить** без разрушения платформы как конструктора.
4. **Модуль использует ядро и службы** — не подменяет их и не строится «вместо» Entity Layer.
5. **Модуль не является инфраструктурой** — не Session Bridge, не Search Service, не Publication.

Критерии согласованы с разделом «Модули» в [Методике классификации](./YASNOPRO_ARCHITECTURE_CLASSIFICATION_METHODOLOGY.md).

### Чат

`component_key`: **`chats-module`**

**Назначение**  
Корпоративный обмен сообщениями внутри компании: личные и групповые диалоги, вложения, упоминания.

**Бизнес-ценность**  
Быстрая коммуникация без внешних мессенджеров; обсуждение работы в контексте компании.

**Почему является модулем**  
Самостоятельная user-facing capability; отключаема; не входит в ядро конструктора.

**Что использует из ядра**  
Объекты (контекст обсуждения), Доступ (кто видит каналы), События (история активности).

**Что использует из служб**  
File Service (вложения), Notification Dispatch Service (упоминания, новые сообщения).

**Что произойдёт при удалении**  
Компания теряет встроенный корпоративный мессенджер.

**Основные пользователи:** Сотрудники, Руководители

**Основные зависимости:** Ядро (Объекты, Доступ, События) → Службы (File, Notification Dispatch)

**Основная категория:** Модули  
**Связанные категории:** Данные, Элементы интерфейса  
**Статус:** Draft  
**Уверенность:** Высокая

### Календарь

`component_key`: **`calendar-module`**

**Назначение**  
Планирование событий компании: встречи, сроки, участники, приглашения.

**Бизнес-ценность**  
Единый корпоративный календарь; координация команды и сроков.

**Почему является модулем**  
Отдельное приложение для пользователя; не обязательно для работы конструктора.

**Что использует из ядра**  
Объекты (события, участники), Связи (привязка к проектам), Доступ, Действия (создать/принять приглашение).

**Что использует из служб**  
Notification Dispatch Service (напоминания, приглашения).

**Что произойдёт при удалении**  
Планирование уходит во внешние календари; теряется связь с объектами платформы.

**Основные пользователи:** Сотрудники, Руководители, Администраторы

**Основные зависимости:** Ядро → Notification Dispatch Service

**Основная категория:** Модули  
**Связанные категории:** Данные  
**Статус:** Draft  
**Уверенность:** Высокая

### Документы

`component_key`: **`document-libraries-module`**

**Назначение**  
Хранение, просмотр и совместная работа с файлами компании: библиотеки документов, версии, совместное редактирование.

**Бизнес-ценность**  
Централизованный документооборот tenant; единое место для регламентов, договоров, проектных файлов.

**Почему является модулем**  
User-facing документооборот; бизнес-пользователь понимает «библиотеки документов».

**Что использует из ядра**  
Объекты (документы как сущности или записи), Доступ (права на библиотеки), Действия (загрузить, согласовать через процесс).

**Что использует из служб**  
File Service (хранение и выдача файлов).

**Что произойдёт при удалении**  
Нет централизованного документооборота; файлы только как вложения к другим объектам.

**Основные пользователи:** Сотрудники, Руководители, Администраторы

**Основные зависимости:** Ядро (Объекты, Доступ) → File Service

**Основная категория:** Модули  
**Связанные категории:** Данные, Службы  
**Статус:** Draft  
**Уверенность:** Высокая

### Уведомления

`component_key`: **`notifications-module`**

**Назначение**  
**Центр уведомлений** для пользователя: колокол, список событий, настройки — «что требует внимания».

**Бизнес-ценность**  
Пользователь не пропускает задачи, комментарии, процессы и системные события.

**Почему является модулем**  
Отдельный продуктовый UX; пользователь открывает уведомления как рабочий инструмент.

**Что использует из ядра**  
События (источник изменений), Доступ (кому показывать), Объекты (контекст уведомления).

**Что использует из служб**  
Notification Dispatch Service — **транспорт доставки**; модуль — **потребление и настройки**.

**Что произойдёт при удалении**  
События платформы не доходят до пользователя в понятном агрегированном виде.

> **Важно:** **Модуль уведомлений ≠ Notification Dispatch Service.**  
> Модуль — UI и продукт для пользователя. Служба — инфраструктура доставки для всех подсистем.

**Основные пользователи:** Все пользователи tenant

**Основные зависимости:** Ядро (События) → Notification Dispatch Service → Модуль уведомлений

**Основная категория:** Модули  
**Связанные категории:** Службы (Notification Dispatch), Элементы интерфейса (колокол)  
**Статус:** Draft  
**Уверенность:** Высокая

### BPMN

`component_key`: **`module-bpmn`**

**Назначение**  
**Визуальный редактор** бизнес-процессов в Studio: диаграммы, шаги, связь с объектами и действиями.

**Бизнес-ценность**  
Аналитик и администратор моделируют регламенты компании в стандартной нотации без программирования.

**Почему является модулем**  
User-facing инструмент проектирования; отделяется от исполнения процессов.

**Что использует из ядра**  
Процессы (модель исполнения), Действия, Объекты, Связи — как элементы диаграммы.

**Что использует из служб**  
Косвенно — Publication Service (доставка опубликованных процессов в runtime).

**Что произойдёт при удалении**  
Процессы можно описывать иначе, но теряется стандартный BPMN-UX платформы.

> **Важно:** **BPMN ≠ Process Engine.**  
> BPMN — модуль **моделирования**. Process Engine — **ядро исполнения** процессов в runtime.

**Основные пользователи:** Аналитики, Администраторы

**Основные зависимости:** Ядро (Процессы, Действия, Объекты) → Studio

**Основная категория:** Модули  
**Связанные категории:** Ядро (Процессы), Публикация  
**Статус:** Draft  
**Уверенность:** Средняя

### ЯСИИ

`component_key`: **`module-yasii`**

**Назначение**  
**Встроенный AI-сотрудник** платформы: диалог, помощь в работе, анализ контекста, рекомендации в рамках прав пользователя.

**Бизнес-ценность**  
Цифровой интеллектуальный сотрудник внутри портала — ускорение решений, объяснимость, работа в контексте компании.

**Почему является модулем**  
Пользователь видит ЯСИИ как отдельную capability; tenant может включать/настраивать модуль.

**Что использует из ядра**  
Доступ (Permission Boundary, Effective Scope), Объекты (контекст данных), Отображения (host surfaces).

**Что использует из служб**  
AI Context Service — **сбор и нормализация контекста**; YASII Runtime — reasoning (архитектурный контур, не модуль v1.0).

**Что произойдёт при удалении**  
Платформа теряет AI-native user surface; остаётся конструктор без встроенного AI-сотрудника.

> **Важно:** **ЯСИИ ≠ AI Context Service.**  
> ЯСИИ — **модуль** (user-facing AI-сотрудник). AI Context Service — **служба** (ContextSnapshot, PermissionBoundary для host surfaces).

**Основные пользователи:** Сотрудники, Руководители, Аналитики, Владелец платформы (Owner Assistant — роль внутри ЯСИИ)

**Основные зависимости:** Session Bridge → AI Context Service → Модуль ЯСИИ; Search Service (discovery контекста)

**Основная категория:** Модули  
**Связанные категории:** Службы (AI Context, Search), Стандарты (Host Integration Contract)  
**Статус:** Draft  
**Уверенность:** Средняя

## 5. Матрица взаимодействия модулей

Человекочитаемая карта типичных связей между модулями v1.0:

```text
Документы
  → Уведомления   (новый документ, согласование)
  → Чат           (обсуждение файла)
  → ЯСИИ          (анализ, вопросы по документу)

Календарь
  → Уведомления   (приглашения, напоминания)
  → Чат           (координация встречи)

Чат
  → Уведомления   (упоминания, новые сообщения)
  → Документы     (вложения, ссылки на библиотеки)

BPMN
  → Уведомления   (шаги процесса, эскалации)
  → Документы     (согласование документов в процессе)
  → Ядро (Процессы) — исполнение после публикации

ЯСИИ
  → Документы     (контекст, цитирование)
  → Чат           (будущие сценарии handoff)
  → Календарь     (контекст событий)
  → все host surfaces через AI Context Service
```

Все модули опираются на **ядро** и **службы**; прямые связи модуль↔модуль — продуктовые сценарии, не дублирование инфраструктуры.

## 6. Границы модулей

### Что не является модулем

Исключение из реестра «Модули» не означает второстепенность. CRM на платформе может быть **важнее** отдельного модуля «Чат» для конкретного клиента — но это **решение**, а не модуль платформы.

### Ядро

Не являются модулями:

- Объекты
- Поля
- Связи
- Доступ
- Действия
- Процессы *(Process Engine — ядро; BPMN — модуль)*
- События
- Навигация
- Композиция портала

### Службы

Не являются модулями:

- Platform Identity Service
- Session Bridge
- Provisioning
- Publication Service
- Deployment Execution Service
- Search Service
- AI Context Service
- Notification Dispatch Service
- File Service

### Runtime

Не являются модулями:

- DEV
- TEMPLATE
- CLIENT

### Компоненты

Не являются модулями:

- PlatformModal
- PlatformTable
- PlatformTabs
- PlatformButton

## 7. Спорные элементы

Элементы ниже **не включены** в состав модулей v1.0. Требуют отдельного решения в документах «Стандарты» или «Решения на платформе».

---

### Оргструктура

**Текущий статус:** Спорный элемент

**Почему может считаться модулем**  
Отдельный административный UX; иерархия подразделений как продукт.

**Почему может считаться стандартом**  
Эталонная **модель компании** (object types «Подразделение», «Должность», связи, представления) — шаблон для всех tenant.

**Почему может считаться решением на платформе**  
Конкретная оргструктура клиента — конфигурация объектов, не capability платформы.

**Проверяемая гипотеза (не окончательное решение):**  
Оргструктура — **не модуль платформы**, а **стандартная модель компании**, собранная из объектов, связей и представлений.

**Предварительное решение:** **не включать в модули v1.0**; классифицировать после документа «Стандарты платформы».

**Следующее действие:** ADR или standard spec «Org Structure Model»; сравнение с tenant admin placeholder.

---

### CRM

**Почему может считаться модулем**  
Packaged CRM как продукт платформы.

**Почему может считаться стандартом**  
Reference object model «Клиент», «Сделка», воронка — seed для TEMPLATE.

**Почему может считаться решением**  
Клиент собирает CRM под себя в Studio.

**Предварительное решение:** **Решение на платформе** (основной путь AOBP); packaged CRM — опциональный **каталог решений**, не модуль v1.0.

**Следующее действие:** каталог решений; не seed в реестр «Модули».

---

### Проекты

**Почему может считаться модулем**  
«Управление проектами» как приложение.

**Почему может считаться стандартом**  
Reference types «Проект», «Этап», Plan View.

**Почему может считаться решением**  
Типичный сценарий конструктора для большинства клиентов.

**Предварительное решение:** **Решение на платформе**; не модуль v1.0.

**Следующее действие:** solution template в TEMPLATE, не registry modules.

---

### Задачи

**Почему может считаться модулем**  
«Мои задачи» как inbox-приложение.

**Почему может считаться стандартом**  
Object type «Задача» + представления + процессы — platform seed pattern.

**Почему может считаться решением**  
Задачи клиента — его object model.

**Предварительное решение:** **Ядро (Объекты + Процессы)** + **решение на платформе**; не модуль v1.0.

**Следующее действие:** зафиксировать в документе «Ядро» связь задач с Process Engine.

---

### Поручения

**Почему может считаться модулем**  
Отдельный продукт «выдать поручение».

**Почему может считаться стандартом**  
Pattern: object «Поручение» + процесс + уведомления.

**Почему может считаться решением**  
Регламент поручений уникален для компании.

**Предварительное решение:** **Решение на платформе**; при необходимости — solution template.

**Следующее действие:** не включать в реестр модулей до product decision.

### Согласования

**Почему может считаться модулем**  
Approval product для документов и решений.

**Почему может считаться стандартом**  
Process pattern + object statuses.

**Почему может считаться решением**  
Маршруты согласования настраиваются под клиента (BPMN + процессы).

**Предварительное решение:** **Решение на платформе** (процессы + BPMN + документы); не отдельный модуль v1.0.

**Следующее действие:** solution template «Согласование документов».

## 8. Решения на платформе

Следующие элементы **не являются модулями платформы**. Это **решения**, собираемые на платформе из:

```text
Объектов
Полей
Связей
Процессов
Отображений
Действий
```

| Решение | Краткое описание |
|---------|------------------|
| **CRM** | Клиенты, сделки, воронка продаж |
| **Проекты** | Проекты, этапы, ресурсы, Plan View |
| **Service Desk** | Обращения, SLA, исполнители |
| **Закупки** | Заявки, поставщики, согласования |
| **Строительство** | Объекты стройки, сметы, этапы |
| **HRM** | Сотрудники, отпуска, кадровые процессы |
| **Оргструктура** *(спорный)* | Подразделения, должности, иерархия |

Платформа поставляет **модули** (Чат, Календарь, …) и **конструктор**; партнёр и клиент собирают **решения** под отрасль и процессы.

Каталог решений — **отдельный продуктовый контур**, не реестр «Модули».

## 9. Использование документа

Документ используется для:

- **наполнения реестра «Модули»** в DEV Studio (после утверждения Draft);
- **классификации новых возможностей** — модуль vs служба vs решение;
- **архитектурного аудита** — «это модуль платформы или решение клиента?»;
- **формирования Release Scope** — изменения модулей влияют на tenant BOM;
- **построения каталога решений** — отделение platform modules от industry solutions.
