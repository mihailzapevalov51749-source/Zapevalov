## 1. Назначение документа

Документ фиксирует **состав и границы ядра** платформы ЯсноПро — категории «Ядро» из [Архитектурной классификации](./YASNOPRO_ARCHITECTURE_CLASSIFICATION.md).

Документ нужен, чтобы:

- иметь единый источник истины для реестра «Ядро платформы» в DEV Studio;
- отделить фундамент конструктора от модулей, служб, runtime, публикации и UI;
- классифицировать новые элементы по [Методике классификации](./YASNOPRO_ARCHITECTURE_CLASSIFICATION_METHODOLOGY.md);
- формировать Release Scope и проводить архитектурный аудит изменений.

Документ основан на аудите **WI-ARCH-CORE-001**, нормализации реестра **WI-ARCH-CORE-004** и синхронизирован с вкладкой «Ядро» Architecture Navigator (**WI-ARCH-DOC-003**).  
Состав ядра v1.2 — **12 платформенных механизмов** (см. раздел 4).  
Техническая реализация, API, структура кода и таблицы БД **не входят** в scope документа.

## 2. Определение ядра платформы

**Ядро платформы ЯсноПро** — это совокупность **базовых механизмов конструктора**, которые позволяют описать компанию: границу организации, объекты, поля, связи, представления, действия, навигацию, доступ и композицию портала.

Ядро — **не** бизнес-данные tenant (экземпляры объектов), **не** модули, **не** визуальные компоненты и **не** инфраструктурные службы.

Ядро — набор механизмов, без которых ЯсноПро перестаёт быть **платформой-конструктором управления компанией** и превращается в обычное приложение с зашитой структурой.

### Главный вопрос ядра

> Если завтра строить платформу заново — какие механизмы реализовать в первую очередь, чтобы остаться конструктором?

Ответ задаёт состав раздела 4.

## 2.1 Архитектурная терминология (WI-ARCH-TERM-001)

В архитектурных документах и реестрах платформы используются **бизнес-термины**, отличные от технических имён в коде (`object_type`, `designer_object_types`, `runtime_entities`).

| Архитектурный термин | Смысл | Примеры | Техническая реализация (не меняется) |
|----------------------|-------|---------|--------------------------------------|
| **Объект** | Вид сущности, которую компания проектирует в конструкторе | Клиенты, Проекты, Задачи, Договоры | `DesignerObjectType`, `object-types-engine` |
| **Экземпляр объекта** | Конкретная запись выбранного объекта | ООО Ромашка, Проект №15, Задача №123 | `RuntimeEntity`, `entity-engine` |

**Классификация (WI-ARCH-CORE-004, WI-ARCH-DOC-003):** **`entity-engine`**, **`process-engine`**, **`event-engine`** — **механизмы ядра** в реестре «Ядро». **Экземпляры объектов** как бизнес-записи tenant и **журналы** как datastore относятся к категории **Данные**; ядро описывает *механизмы* runtime — создание и версионирование записей, исполнение процессов, фиксацию событий — а не сами таблицы хранения.

**Запрещено в архитектурной prose:** переносить в документы legacy-технику `object_type` / `object-types` как название механизма платформы — вместо неё используются **Объект** и **Экземпляр объекта** (см. таблицу выше).

## 3. Критерии включения в ядро

Элемент включается в ядро v1.2, если выполняются **все** условия:

1. Элемент является **базовым механизмом конструктора**, а не продуктовой функцией.
2. **Без него невозможно описать компанию** как систему — объекты, связи, права, представления, композицию портала (не обязательно хранить бизнес-записи).
3. Элемент **используется несколькими** модулями и службами платформы.
4. Элемент **не является отключаемой** бизнес-функцией (чат, календарь, документы).
5. Элемент **не является только** визуальным компонентом или зоной интерфейса.
6. Элемент **не является только** инфраструктурной службой (provisioning, publication, session bridge).

Критерии согласованы с разделом «Ядро» в [Методике классификации](./YASNOPRO_ARCHITECTURE_CLASSIFICATION_METHODOLOGY.md).

### Компания

**Определение**  
Базовый контейнер платформы, внутри которого существуют пользователи, объекты, данные, настройки и рабочее пространство организации.

**Почему входит в ядро**  
Без понятия «компания» нет конструктора компаний — только одна общая среда. Граница tenant — фундамент изоляции (ADR-SEC-001, ADR-PROV-001).

**Что произойдёт, если убрать**  
Платформа не масштабируется на множество клиентов; теряется смысл B2B-конструктора.

**Основная категория:** Ядро  
**Связанные категории:** Службы (Provisioning), Runtime, Конфигурация 
**Статус:** Active (реестр)  
**Уверенность:** Высокая

---

### Движок объектов

**Определение**  
Источник истины бизнес-данных tenant: записи объектов и их версии.

**Почему входит в ядро**  
Без механизма runtime-сущностей конструктор не может материализовать спроектированные объекты в рабочие записи компании.

**Что произойдёт, если убрать**  
Office теряет единый слой CRUD и версионирования; представления и действия не имеют данных для работы.

**Основная категория:** Ядро  
**Связанные категории:** Данные (business-records-data, runtime values)  
**Статус:** Active (реестр)  
**Уверенность:** Высокая

---

### Объект

**Определение**  
Универсальный инструмент конструктора, предназначенный для описания любой сущности компании: клиента, проекта, договора, сотрудника, задачи, документа и других элементов деятельности.

**Почему входит в ядро**  
Без объектов как инструмента конструктора платформа не проектируется под любую компанию — остаётся фиксированный набор сущностей.

**Что произойдёт, если убрать**  
Невозможно добавить «Проект», «Задачу», «Клиента» через конструктор.

**Основная категория:** Ядро  
**Связанные категории:** Данные (метаданные), Стандарты  
**Статус:** Active (реестр)  
**Уверенность:** Высокая

---

### Поля

**Определение**  
Атрибуты объекта, определяющие какие данные могут храниться в экземплярах объекта.

**Почему входит в ядро**  
Объект без полей — пустая оболочка; конструктор не может описать структуру данных компании.

**Что произойдёт, если убрать**  
Нельзя задать статус, срок, ответственного — только безликие записи.

**Основная категория:** Ядро  
**Связанные категории:** Данные, Стандарты  
**Статус:** Active (реестр)  
**Уверенность:** Высокая

---

### Связи

**Определение**  
Механизм установления отношений между объектами и их экземплярами, позволяющий формировать единую модель данных компании.

**Почему входит в ядро**  
Конструктор без связей — набор изолированных списков, а не модель компании.

**Что произойдёт, если убрать**  
Невозможны иерархии, сквозные сценарии; данные превращаются в несвязанные таблицы.

**Основная категория:** Ядро  
**Связанные категории:** Данные (экземпляры и relation instances)  
**Статус:** Active (реестр)  
**Уверенность:** Высокая

---

### Представления

**Определение**  
Способы отображения объектов и их данных для пользователя: таблицы, карточки, планы, календари и другие формы визуализации.

**Почему входит в ядро**  
Разделение «механизм представления / бизнес-данные» — базовый принцип конструктора; представления не заменяют слой данных.

**Что произойдёт, если убрать**  
Нельзя настроить разные способы работы с одними объектами; данные и экраны сливаются.

**Основная категория:** Ядро  
**Связанные категории:** Элементы интерфейса, Компоненты  
**Статус:** Active (реестр)  
**Уверенность:** Высокая

---

### Действия

**Определение**  
Операции, которые могут выполняться над объектами, экземплярами объектов и другими элементами платформы.

**Почему входит в ядро**  
Без действий конструктор не собирает рабочие сценарии — остаётся только просмотр.

**Что произойдёт, если убрать**  
Интерфейс статичен; автоматизация и процессы теряют точки входа.

**Основная категория:** Ядро  
**Связанные категории:** Элементы интерфейса (размещение кнопок), Модули (процессы)  
**Статус:** Active (реестр)  
**Уверенность:** Высокая

---

### Движок событий

**Определение**  
Журналы событий, аудит и dev-development записи.

**Почему входит в ядро**  
Платформе нужен единый механизм фиксации событий и аудита — не только хранилище записей, но и контракт emit/consume для всех контуров.

**Что произойдёт, если убрать**  
Теряется сквозная трассируемость изменений; службы и модули не могут согласованно писать и читать события.

**Основная категория:** Ядро  
**Связанные категории:** Данные (event-journal-core, audit datastore)  
**Статус:** Active (реестр)  
**Уверенность:** Высокая

---

### Навигация

**Определение**  
Механизм организации перемещения пользователя по платформе и доступа к её разделам, объектам и функциям.

**Почему входит в ядро**  
Без навигации спроектированный портал не собирается в целостную рабочую среду tenant.

**Что произойдёт, если убрать**  
Пользователь «застревает» на отдельных экранах; конструктор не описывает структуру компании целиком.

**Основная категория:** Ядро  
**Связанные категории:** Элементы интерфейса, Конфигурация 
**Статус:** Active (реестр)  
**Уверенность:** Высокая

---

### Доступ

**Определение**  
Механизм управления правами пользователей, определяющий кто, что и в каком объёме может видеть, изменять или выполнять.

**Почему входит в ядро**  
Multi-tenant конструктор без прав непригоден для B2B; нарушается изоляция компаний (ADR-SEC-001).

**Что произойдёт, если убрать**  
Данные компаний смешиваются; платформа теряет доверие владельца и клиентов.

**Основная категория:** Ядро  
**Связанные категории:** Конфигурация, Службы (session routing)  
**Статус:** Active (реестр)  
**Уверенность:** Высокая

---

### Композиция портала

**Определение**  
Механизм построения пользовательского пространства компании из страниц, секций, блоков, объектов, модулей и элементов интерфейса.

**Почему входит в ядро**  
Конструктор порталов без композиции — только модель данных без «места работы» пользователя.

**Что произойдёт, если убрать**  
Есть объекты и представления, но нельзя спроектировать рабочее место сотрудника.

**Основная категория:** Ядро  
**Связанные категории:** Элементы интерфейса  
**Статус:** Active (реестр)  
**Уверенность:** Высокая

---

### Движок процессов

**Определение**  
Исполнение бизнес-процессов поверх объектов и действий.

**Почему входит в ядро**  
Process Engine — базовый механизм автоматизации конструктора; BPMN-модуль (`module-bpmn`) — продуктовая оболочка, а не замена движка.

**Что произойдёт, если убрать**  
Автоматизация сценариев tenant невозможна; остаются только ручные действия без оркестрации.

**Основная категория:** Ядро  
**Связанные категории:** Модули (module-bpmn), Данные (process instances)  
**Статус:** Active (реестр)  
**Уверенность:** Высокая

## 6. Границы ядра

### Что ядро делает

- Описывает **модель компании** как систему объектов, полей, связей, прав, представлений, действий, навигации и композиции портала.
- Задаёт **механизмы конструктора**, через которые tenant проектирует рабочую среду.
- Включает **runtime-механизмы** (`entity-engine`, `process-engine`, `event-engine`) — не путать с datastore-элементами реестра «Данные».

### Что ядро не делает

- Не заменяет **datastore-элементы** реестра «Данные» (`business-records-data`, `event-journal-core`) — ядро задаёт механизм, данные — хранение
- Не доставляет изменения между DEV, TEMPLATE и CLIENT → **Службы / Публикация**
- Не создаёт физические среды и БД компаний → **Службы (Provisioning)**
- Не предоставляет чат, календарь, документы → **Модули**
- Не задаёт визуальные виджеты PlatformModal, PlatformTable → **Компоненты**
- Не управляет глобальным lifecycle платформы → **Control Plane** (контур, не ядро)
- Не является режимом «Studio» или «Office» → **подсистемы**, использующие ядро

### Граница: ядро ↔ данные

| Ядро | Данные |
|------|--------|
| Объект, поля, связи (design-time механизмы) | Экземпляры объектов как бизнес-записи, runtime values |
| `entity-engine` (механизм CRUD/версий) | `business-records-data` (datastore) |
| `event-engine` (механизм emit/audit) | `event-journal-core` (хранилище журналов) |
| Представления (способ показа) | Version pins, catalog snapshots |
| Доступ (модель прав) | Membership profiles как данные tenant |

### Граница: ядро ↔ службы

| Ядро | Службы |
|------|--------|
| Механизм «как устроена компания» | Механизм «как платформа обслуживает» tenant |
| Доступ как модель прав | Session Bridge, Provisioning, Publication |
| AI Context (не ядро) | `ai-context-engine` как сервис контекста |

### Граница: ядро ↔ модули

| Ядро | Модули |
|------|--------|
| Обязательно для любого tenant | Можно отключить без разрушения конструктора |
| Объект, связи, действия, представления | Чат, календарь, уведомления, документы |
| `process-engine` (механизм исполнения) | `module-bpmn` (редактор/UX процессов) |

### Граница: ядро ↔ интерфейс

| Ядро | Элементы интерфейса |
|------|---------------------|
| Навигация как структура переходов | Меню, панели как UI-зоны |
| Композиция портала как модель экранов | Конкретные страницы и layout |
| Представления как способ показа данных | Размещение view на экране |

### Граница: ядро ↔ runtime

| Ядро | Runtime |
|------|---------|
| Логика конструктора | DEV / TEMPLATE / CLIENT как среды |
| Модель компании (логическая граница) | Materialization slot, per-company runtime |

### Граница: ядро ↔ публикация

| Ядро | Публикация / Конфигурация |
|------|------------|
| Объект, поля, связи (design-time) | Release Package, Scope, Candidate |
| Каталог опубликованной структуры (`published-catalog`) | Materialized publish snapshot tenant |

## 7. Матрица зависимостей ядра

Человекочитаемая карта «кто от кого зависит» внутри **12 механизмов** ядра v1.2:

```text
Компания
→ ограничивает все механизмы внутри границы tenant
→ задаёт контекст для Доступа

Движок объектов
→ материализует Объект в runtime-записи tenant
→ используется Представлениями, Действиями, Движком процессов
→ ограничен Доступом

Объект
→ использует Поля
→ использует Связи (определения)
→ используется Представлениями и Действиями
→ размещается в Композиции портала

Поля
→ входят в Объект
→ описывают структуру данных для экземпляров (слой Данные)

Связи
→ связывают объекты и их экземпляры (runtime — слой Данные)
→ учитываются в Представлениях и Действиях

Представления
→ показывают объекты и данные (через Движок объектов)
→ размещаются в Композиции портала
→ доступны через Навигацию

Действия
→ выполняются над объектами и экземплярами (runtime)
→ размещаются в Композиции портала
→ ограничены Доступом

Движок событий
→ фиксирует изменения и аудит для всех механизмов
→ связан с datastore реестра «Данные», но не заменяет его

Навигация
→ связывает экраны Композиции портала
→ учитывает Доступ

Доступ
→ применяется ко всем механизмам и runtime-операциям tenant

Композиция портала
→ содержит Представления, Действия, модули и UI-элементы
→ связана с Навигацией

Движок процессов
→ оркестрирует сценарии поверх Действий и Движка объектов
→ дополняется модулем BPMN, но не заменяется им
```

**Связанные категории вне матрицы:** datastore-элементы реестра «Данные» и продуктовые модули используют механизмы ядра (раздел 5).

### Порядок реализации (архитектурный)

```text
Фаза 0 — описать компанию:
  Компания → Объект → Поля → Связи → Доступ

Фаза 1 — runtime-данные:
  Движок объектов → runtime values (datastore — реестр «Данные»)

Фаза 2 — собрать портал:
  Представления → Действия → Композиция портала → Навигация

Фаза 3 — автоматизировать и трассировать:
  Движок процессов → Движок событий (datastore журналов — реестр «Данные»)
```

## 8. Что не относится к ядру v1.2

Следующие элементы **важны для платформы**, но их **основная категория другая**:

| Элемент | Registry `component_key` | Основная категория |
|---------|--------------------------|-------------------|
| Каталог опубликованной структуры | `published-catalog` | **Конфигурация** |
| AI Context Engine | `ai-context-engine` | **Службы** |
| Event Journal Core | `event-journal-core` | **Данные** |
| Business records datastore | `business-records-data` | **Данные** |
| Session Bridge | — | Службы |
| Provisioning | — | Службы |
| Publication pipeline | — | Службы |
| Release Scope | — | Архив / governance |
| DEV / TEMPLATE / CLIENT Runtime | — | Конфигурация / Runtime |
| PlatformModal | — | Компоненты |
| PlatformTable | — | Компоненты |
| Чат | `chats-module` | Модули |
| Календарь | `calendar-module` | Модули |
| Уведомления | `notifications-module` | Модули |
| Документы | `document-libraries-module` | Модули |
| BPMN (редактор) | `module-bpmn` | Модули |
| ЯСИИ | `module-yasii` | Модули |
| Control Plane | — | Контур управления (не ядро) |
| Studio (режим работы) | — | Подсистема / UX-контур |

**Важно:** исключение из ядра не означает второстепенность. Datastore, Publication и Runtime критичны для эксплуатации — но они **не входят** в реестр «Ядро» (12 механизмов конструктора).

## 9. Использование документа

Документ используется для:

- **наполнения реестра «Ядро»** в DEV Studio (синхронизировано с WI-ARCH-CORE-004);
- **классификации новых элементов** по методике;
- **формирования Release Scope** — изменения ядра требуют повышенного архитектурного контроля;
- **проверки архитектурных изменений** — «затрагивает ли изменение фундамент конструктора?»;
- **аудита платформы** — сопоставление AS-IS с целевым составом ядра;
- **подготовки следующих документов** — службы, модули, runtime, публикация.
